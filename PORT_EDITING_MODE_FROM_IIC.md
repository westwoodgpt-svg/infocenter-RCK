# Задача: перенести «режим редактирования» из Инфоцентра ИИЦ в Инфоцентр РЦК

Этот файл — бриф для сессии Claude Code, у которой в чате основным подключён
репозиторий **`westwoodgpt-svg/infocenter-RCK`** (этот репозиторий). Цель — добавить
сюда тот же редактируемый конструктор карточек, что уже реализован и работает в
**`westwoodgpt-svg/infocenter-IIC`** (публичный репозиторий, ветка `master`).
Смотреть на ИИЦ как на образец «как это должно быть устроено» — по коду, по
структуре файлов, по UX. Ниже — что именно там сделано и что важно решить
*перед* переносом, потому что два ключевых архитектурных момента в РЦК
отличаются от ИИЦ и слепое копирование кода их сломает.

Эталонный коммит ИИЦ на момент написания этого брифа: `646e2f2`
(https://github.com/westwoodgpt-svg/infocenter-IIC). Полная история от
`94f7821` («Собрать инфоцентр ИИЦ по образцу Инфоцентра РЦК») до `646e2f2`
описывает именно ввод редактора карточек и синхронизации — стоит просмотреть
`git log` в этом репозитории для деталей каждого шага.

## Что такое «режим редактирования» в ИИЦ (кратко)

Кнопка в шапке переключает вкладку между просмотром и редактированием. В
режиме редактирования на любой из 5 вкладок можно:

- добавлять / редактировать / удалять карточки пяти типов: **KPI**
  (план/факт/%), **График** (столбчатый/линейный/с областями/круговой, данные
  задаются таблицей «категория × ряды»), **Смета** (план/факт), **Список**,
  **Ответственный** (с автоподстановкой ФИО/фото/должности из сотрудников
  Битрикс24);
- менять порядок карточек стрелками вверх/вниз;
- очистить вкладку и собрать инфоцентр с нуля, или сбросить к стартовому
  примеру;
- экспортировать/импортировать весь дашборд JSON-файлом.

Если приложение открыто внутри Битрикс24 (iframe), все изменения сохраняются
в общих данных портала и видны любому сотруднику, а не только автору правки
(с оговоркой last-write-wins — без слияния одновременных правок). Вне
Битрикс24 (прямое открытие в браузере, `npm run dev`) всё работает на
`localStorage` конкретного браузера — это же используется для локальной
разработки редактора без захода в портал.

Подробное описание пользовательской логики — в
[`README.md` репозитория ИИЦ](https://github.com/westwoodgpt-svg/infocenter-IIC/blob/master/README.md),
он написан подробно и стоит прочитать целиком перед переносом.

## Как это устроено в коде (файл за файлом)

### Модель данных — `src/types.ts`

```ts
export type TabId = 'security' | 'quality' | 'production' | 'costs' | 'personnel';
export type ChartType = 'bar' | 'line' | 'area' | 'pie';
export type CardType = 'kpi' | 'chart' | 'money' | 'list' | 'person';

interface BaseCard { id: string; type: CardType; title: string; subtitle?: string; }

export interface KpiCard extends BaseCard {
  type: 'kpi'; planValue: string; planDate?: string; factValue: string; factDate?: string; percent: number | null;
}
export interface ChartRow { category: string; values: number[]; }
export interface ChartCard extends BaseCard {
  type: 'chart'; chartType: ChartType; seriesNames: string[]; rows: ChartRow[];
}
export interface MoneyCard extends BaseCard { type: 'money'; plan: number; fact: number; }
export interface ListCard extends BaseCard { type: 'list'; items: string[]; }
export interface PersonCard extends BaseCard { type: 'person'; role: string; tags: string[]; note?: string; photoUrl?: string; }

export type AnyCard = KpiCard | ChartCard | MoneyCard | ListCard | PersonCard;
export type DashboardState = Record<TabId, AnyCard[]>;
```

Обратите внимание: `TabId` — те же 5 вкладок, что уже есть в РЦК
(`security | quality | production | costs | personnel`), это не случайно —
ИИЦ изначально собирался по образцу РЦК.

### Фронтенд-слой конструктора (новые файлы в ИИЦ, их нет в текущем РЦК)

| Файл | Роль |
|---|---|
| `src/seedData.ts` | `SEED_DATA` (стартовый пример) + `EMPTY_DASHBOARD` (все вкладки пустые) |
| `src/store.ts` | Хук `useDashboardStore()` — состояние дашборда, CRUD карточек (`addCard/updateCard/deleteCard/moveCard`), синхронизация с Битрикс24 (pull при монтировании и при возврате на вкладку, push при каждом изменении), кэш в `localStorage` как офлайн-копия |
| `src/bitrix.ts` | Обёртка над `window.BX24`: `bx24Init`, `isInIframe`, `fetchDashboardOption` (чтение `app.option.get`), `saveDashboardOption` (POST на `/api/save-dashboard`), `fetchPortalUsers` (постраничный `user.get` для выбора «Ответственного») |
| `src/usePortalUsers.ts` | Модульный кэш + хук над `fetchPortalUsers`, чтобы список сотрудников не перезапрашивался при каждом открытии модалки |
| `src/components/TabBoard.tsx` | Сетка карточек текущей вкладки + кнопка «Добавить карточку» + пустое состояние |

| `src/components/cards/CardShell.tsx` | Обёртка карточки: в режиме редактирования показывает панель «вверх/вниз/редактировать/удалить» |

| `src/components/cards/{Kpi,Chart,Money,List,Person}CardView.tsx` | Рендер каждого типа карточки (график — через Recharts, тот же паттерн, что уже используется в панелях РЦК) |
| `src/components/cards/palette.ts` | Палитра цветов рядов для графиков |
| `src/App.tsx` | Шапка: бейдж режима синхронизации (Битрикс24 / автономный), кнопка «Обновить», переключатель «Режим редактирования/просмотра», меню ⚙ (экспорт/импорт JSON, сброс, очистка) |

### Бэкенд-слой общих данных (это критичная часть — см. секцию про Cloudflare ниже)

Проблема, которую решает бэкенд: `app.option.set` в Битрикс24 доступен только
администраторам портала. Если бы браузер каждого сотрудника писал в
`app.option` напрямую своим токеном, редактировать дашборд мог бы только
админ. Решение в ИИЦ:

1. Браузер шлёт изменения на `/api/save-dashboard` вместе со своим
   пользовательским токеном (`BX24.getAuth()`).
2. Сервер проверяет, что это действующая сессия портала (`profile`), и сам
   пишет в `app.option` — но отдельным **сервисным токеном**, изначально
   полученным от администратора.
3. Сервисный токен сервер ловит автоматически: когда администратор портала
   открывает приложение (POST от Битрикс24 с `AUTH_ID`/`REFRESH_ID`), сервер
   через `profile` проверяет, что открывший — админ, и сохраняет его токен
   как сервисный. Обновляется через `refresh_token`, пока админ хоть изредка
   открывает приложение.

Файлы (все — **Vercel Node.js serverless functions**, `export default async
function handler(req, res)`, читают `req.body`, используют Node `fs`):

| Файл | Роль |
|---|---|
| `api/_bitrixAuth.js` | Обмен `REFRESH_ID` → полноценный токен через `oauth.token` (`https://oauth.bitrix.info/oauth/token/`, нужны `BITRIX_CLIENT_ID`/`BITRIX_CLIENT_SECRET`), проверка `ADMIN` через `profile`, хранение сервисного токена в **Redis** через `ioredis` (`REDIS_URL`), `verifyUserToken`, `bxAppOptionSet` |
| `api/save-dashboard.js` | POST-эндпоинт: проверяет пользовательский токен, пишет `app.option` через сервисный токен |
| `api/bitrix-status.js` | Диагностика (`/api/bitrix-status`): есть ли `REDIS_URL`/креды, валиден ли сервисный токен, что случилось при последней попытке его поймать — без раскрытия самого токена |
| `api/serve.js` | Раздаёт `dist/` на любой HTTP-метод (Битрикс24 открывает приложение POST-ом); на POST дополнительно вызывает `maybeCaptureServiceToken` из `_bitrixAuth.js` |
| `vercel.json` | Роутинг: `/api/save-dashboard` и `/api/bitrix-status` — на свои функции, всё остальное — на `api/serve` |

Инфраструктура на Vercel (см. README ИИЦ, раздел «Обязательная настройка на
Vercel»): подключить **Redis Cloud** (Storage → Create Database → Redis,
Custom Prefix `REDIS` → Vercel сам создаёт `REDIS_URL`), задать
`BITRIX_CLIENT_ID`/`BITRIX_CLIENT_SECRET` в Environment Variables, один раз
попросить админа портала открыть приложение.

## ⚠️ Два решения, которые нужно принять ДО переноса кода — не угадывать

### 1. РЦК сегодня — не конструктор карточек, а витрина живых Списков Битрикс24

В отличие от ИИЦ (который живёт на ручных карточках + `app.option`), текущий
`src/App.tsx` РЦК тянет данные напрямую из **11 Списков Битрикс24** (ID
78–88, константа `LISTS` в `App.tsx`) через `BX24.callMethod('lists.element.get', …)`
прямо из браузера, парсит их в строго типизированную `RckDashboardData`
(`src/types.ts`) и рендерит через 5 специализированных компонентов
(`SecurityPanel`, `QualityPanel`, `ProductionPanel`, `CostsPanel`,
`PersonnelPanel` — фиксированные графики под конкретную форму данных, не
универсальные карточки). Чтения не ограничены правами — поэтому у РЦК никогда
не было нужды в сервисном токене и записи через сервер, вся синхронизация
сегодня — read-only и идёт напрямую браузер → Битрикс24.

Перенос редактора «как есть» означает **замену** этой автоматической
синхронизации со Списками на ручное редактирование карточек. Это не мелочь —
не решайте это самостоятельно, нужно уточнить у пользователя один из
вариантов:

- **(A) Полная замена** — выкинуть `LISTS`/`RckDashboardData`/панели,
  перейти на карточки как в ИИЦ, содержимое переносить в карточки вручную
  через сам редактор (Списки Битрикс24 перестают быть источником данных).
- **(B) Добавка поверх** — оставить существующие панели и автосинхронизацию
  как есть (это система читает Списки и не должна сломаться), а редактор
  карточек добавить как отдельный слой — например, дополнительные
  произвольные карточки на каждой вкладке поверх автоматических графиков,
  либо отдельная 6-я вкладка/секция.
- **(C) Гибрид** — оставить автосинхронизацию из Списков как основной
  механизм, но дать возможность вручную переопределять/дополнять отдельные
  показатели через `app.option`, если Список недоступен или нужен ручной
  пункт вне структуры Списков.

**Спросите пользователя явно, прежде чем трогать `App.tsx`, `data.ts`,
`types.ts` или панели РЦК.**

### 2. РЦК хостится на Cloudflare Workers, а не на Vercel — бэкенд ИИЦ нужно переписывать под Workers

`DEPLOYMENT.md` этого репозитория фиксирует: боевой хостинг РЦК —
**Cloudflare Workers** (`wrangler.jsonc` + `worker.js`, деплой
`npx wrangler deploy`, URL `https://infocenterrck.westwoodgpt.workers.dev/`).
`worker.js` сегодня делает только одно — переигрывает POST в GET и отдаёт
статику; никакого разбора `AUTH_ID`/`REFRESH_ID`, никакого сервисного токена,
никакого KV/Redis тут нет.

В репозитории также лежат `vercel.json` и `api/serve.js` (Node-style,
`export default function handler(req, res)`, `fs.readFileSync`) — похоже,
Vercel рассматривался как запасной вариант хостинга (в README ИИЦ тоже есть
ссылка на этот запасной вариант), но сейчас это не то, что реально
обслуживает пользователей.

**Код `api/_bitrixAuth.js` / `api/save-dashboard.js` / `api/bitrix-status.js`
из ИИЦ нельзя скопировать в РЦК как есть, если РЦК продолжает работать на
Cloudflare Workers** — это два разных рантайма:

- Vercel serverless functions: Node.js, `req`/`res` в стиле Express/http,
  обычный `fetch` к внешним URL, `ioredis` — TCP-клиент, которому нужен
  Node net-стек (в Workers его нет).
- Cloudflare Workers: `fetch(request, env)` хендлер, нет Node `fs`/`net`;
  вместо `ioredis`+`REDIS_URL` для хранения одного сервисного токена
  естественный аналог — **Cloudflare KV** (или Durable Object), доступный
  через `env` без TCP-подключения. Обмен `refresh_token` на `oauth.token`
  делается обычным `fetch`, это работает в Workers без изменений.

Варианты:

- **Переписать** `_bitrixAuth.js`/`save-dashboard`/`bitrix-status` на Workers
  API + KV-биндинг, добавить обработку `AUTH_ID`/`REFRESH_ID` POST-тела в
  `worker.js` (сейчас он его не читает вообще).
- **Или мигрировать хостинг РЦК на Vercel** и переиспользовать код ИИЦ почти
  без изменений (в репозитории уже есть заготовка `vercel.json`/`api/serve.js`
  под это, но, судя по `DEPLOYMENT.md`, раньше эта заготовка не взлетела —
  стоит перепроверить, почему, прежде чем на неё полагаться).

**Тоже уточните у пользователя, какой путь предпочтителен**, прежде чем
писать бэкенд — это влияет на объём работы и на процесс деплоя.

## Рекомендуемый порядок действий для исполняющей сессии

1. Прочитать `README.md` и весь `git log` репозитория ИИЦ (`master`) — там
   история именно этой фичи, коммит за коммитом, с объяснениями в сообщениях.
2. Задать пользователю два вопроса выше (архитектура данных / хостинг),
   прежде чем менять код.
3. В зависимости от ответов — либо переносить конструктор карточек по
   образцу файлов из таблиц выше (адаптируя цветовую тему/название `ИИЦ` →
   не нужно, у РЦК уже своё название и фирменный `<|ЦК>` в шапке — это
   трогать не нужно, конструктор ортогонален брендингу), либо встраивать его
   рядом с существующими панелями.
4. Если бэкенд общих данных нужен — реализовать по протоколу из раздела
   «Бэкенд-слой» выше, под выбранный рантайм (Workers+KV или Vercel+Redis).
   Не забыть уникальный `OPTION_KEY` (в ИИЦ — `iic_dashboard_v1`; для РЦК
   нужен свой, например `rck_dashboard_v1`, чтобы не пересекаться, если
   когда-либо оба приложения окажутся в одном Redis/KV) и отдельный ключ
   сервисного токена (в ИИЦ — `iic:bx-service-token`).
5. Проверить локально: `npm run dev` (автономный режим, `localStorage`) и
   `npm run lint` (`tsc --noEmit`).
6. Если добавляли зависимость `ioredis` (вариант Vercel) — добавить в
   `package.json`; если Workers+KV — зависимостей не требуется, но нужно
   добавить `kv_namespaces` в `wrangler.jsonc` и создать namespace
   (`npx wrangler kv namespace create ...`).
7. Не менять `LISTS`/`RckDashboardData`/существующие панели без явного
   решения по пункту 1 выше.
