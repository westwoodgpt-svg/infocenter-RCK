# Инфоцентр на своём сервере (без Vercel)

Вместо serverless-функций Vercel работает один Node.js-процесс
(`server/index.js`) за nginx с сертификатом Let's Encrypt. Данные хранятся в Redis
на этом же сервере, вложения витрины — на его диске
(`/var/lib/infocenter-rck/uploads`). Код тот же, что на Vercel: обработчики
`api/*.js` подключены к Express без изменений.

| Что | Где на сервере |
|---|---|
| Код | `/opt/infocenter-rck` |
| Настройки (секреты) | `/etc/infocenter-rck.env` |
| Вложения витрины | `/var/lib/infocenter-rck/uploads` |
| Служба | `systemctl status infocenter-rck`, логи — `journalctl -u infocenter-rck -f` |
| nginx | `/etc/nginx/sites-available/infocenter-rck` |
| Redis | `redis-server`, только localhost, с записью на диск (appendonly) |

Нужны Ubuntu 22.04/24.04 или Debian 12, доступ root, открытые порты 80 и 443
и домен, который указывает на сервер (у хостинга он уже есть, например
`infocenter.2.27.10.126.nip.io`; имя `vm1101304.hosted-by.u1host.com` в
публичном DNS не существует, его не используйте).

## Переезд с Vercel по шагам

1. **Установка.** Зайдите на сервер по SSH под root и выполните:

   ```bash
   BRANCH=main
   curl -fsSL "https://raw.githubusercontent.com/westwoodgpt-svg/infocenter-RCK/$BRANCH/deploy/install.sh" -o install.sh
   DOMAIN=infocenter.2.27.10.126.nip.io BRANCH=$BRANCH bash install.sh
   ```

   Скрипт поставит Node.js 22, Redis, nginx и certbot, соберёт приложение,
   запустит службу и получит HTTPS-сертификат. `BRANCH` — ветка, из которой
   брать код: если изменения ещё не влиты в `main`, укажите их ветку.

2. **Секреты.** Откройте `/etc/infocenter-rck.env` (`nano /etc/infocenter-rck.env`)
   и перенесите значения из Vercel → проект → **Settings → Environment
   Variables**: `BITRIX_CLIENT_ID`, `BITRIX_CLIENT_SECRET` и, если были заданы,
   переменные `INFOCENTER_*`. `REDIS_URL` не меняйте — он уже указывает на
   локальный Redis. Затем выполните `systemctl restart infocenter-rck`.

3. **Данные.** Скопируйте из Vercel строку `REDIS_URL` (Settings → Environment
   Variables) и выполните:

   ```bash
   OLD_REDIS_URL='redis://default:…@…:…' bash /opt/infocenter-rck/deploy/migrate.sh
   ```

   Переносятся все ключи `rck:*`: инфоцентры отделов, витрина, история версий,
   личные настройки сводного экрана, сервисный токен. Ключи ИИЦ (`iic:*`),
   если база общая, не трогаются. Вложения витрины из Vercel Blob
   скачиваются на диск, ссылки на них переписываются. В конце скрипт
   показывает сверку «было → стало» по каждому инфоцентру (см. «Как не
   потерять данные инфоцентра РЦК» ниже).

4. **Проверка.** Откройте `https://<домен>/api/bitrix-status` — там должно быть
   `"ok": true`, `hasBitrixCreds: true`, а в `dashboard` — число карточек.

5. **Повторный перенос прямо перед переключением.** Пока портал смотрит на
   Vercel, сотрудники могут что-то править там. Чтобы ничего не потерять,
   повторите шаг 3 с `FORCE=1` непосредственно перед шагом 6:

   ```bash
   FORCE=1 OLD_REDIS_URL='redis://…' bash /opt/infocenter-rck/deploy/migrate.sh
   ```

   `FORCE=1` перезаписывает данные на сервере данными с Vercel, поэтому после
   переключения портала его больше не запускайте.

6. **Переключение портала.** Битрикс24 → Приложения → Разработчикам → ваше
   локальное приложение: **путь обработчика** (и путь установки, если задан)
   поменяйте на `https://<домен>/`. Сохраните, затем администратор портала
   должен **один раз открыть приложение** (полная перезагрузка страницы).

7. После нескольких дней спокойной работы проект на Vercel можно удалить
   (или хотя бы отключить в нём автодеплой).

## Как не потерять данные инфоцентра РЦК

Инфоцентр РЦК хранится в Redis под ключами `rck:board:rck:*`. Туда же
относятся ключи до разделения по отделам (`rck:dashboard:current`), история
карточек (`rck:card-history:*`) и копия у отдела РЦК (`rck:board:dept-<id>:*`).
Перенос копирует все ключи `rck:*`, и картинки из карточек тоже: они лежат
прямо в данных. Плюс:

- **Резервная копия.** Перед копированием скрипт сохраняет все инфоцентры с
  Vercel в `/var/lib/infocenter-rck/backup-from-vercel-<дата>.json`.
- **Сверка.** После переноса каждый инфоцентр сравнивается «было → стало»
  (номер версии и карточки по вкладкам), инфоцентр РЦК помечен отдельно.
  При расхождении скрипт завершается с ошибкой, и портал переключать нельзя.
  Сверить ещё раз без переноса: `VERIFY=1 OLD_REDIS_URL='…' bash deploy/migrate.sh`.
- **`INFOCENTER_LEGACY_DEPARTMENT_ID` переносите точно как на Vercel** (или не
  задавайте, если там её не было). Эта переменная решает, в каком инфоцентре
  открываются данные РЦК: с другим значением данные останутся в Redis, но
  появятся не там, где их ждут.
- **Несохранённое в браузерах.** Кэш браузера привязан к адресу сайта, поэтому
  после смены адреса правки, которые не дошли до портала, на новом сервере не
  появятся. Перед переключением попросите коллег обновить инфоцентр и
  убедиться, что в шапке нет «Не сохранилось в Битрикс24».
- **Независимая копия руками.** Перед переключением откройте в инфоцентре
  РЦК меню «⚙» → «Экспортировать JSON» и сохраните файл. Если что-то пойдёт не
  так, его можно загрузить обратно через «Импортировать JSON».

## Сотрудники в «автономном режиме» и недостающие инфоцентры

**Причина.** Раньше библиотека Битрикс24 подключалась с `api.bitrix24.com`
через устаревший `document.write`. Если она не загружалась (Chrome блокирует
такие скрипты на медленной сети, их режут блокировщики рекламы и фильтры
корпоративной сети), приложение **молча** переходило в автономный режим. Всё,
что сотрудник вносил, сохранялось только в его браузере и на сервер не
попадало. Поэтому инфоцентров этих отделов не было в Redis на Vercel, и
переносить их было нечего.

**Что исправлено:**
- библиотека грузится надёжно: сначала с `api.bitrix24.com`, при неудаче —
  копия с нашего сервера (`/api/bx24-sdk`, хранится в
  `/var/lib/infocenter-rck/bx24-sdk.js`);
- внутри портала приложение больше не уходит в автономный режим: если связи
  с Битрикс24 нет, оно показывает красное предупреждение и запрещает правку,
  чтобы ничего не потерялось;
- открытое напрямую (не через портал) приложение явно предупреждает, что
  правки останутся только в этом браузере;
- **карточки, оставшиеся в браузере, не потеряны.** Когда сотрудник, работавший
  в автономном режиме, откроет инфоцентр на портале, приложение покажет
  «В этом браузере остались карточки…» и кнопку **«Добавить в этот
  инфоцентр»**. Карточки добавятся в инфоцентр его отдела, существующие не
  изменятся. Автономная копия не удаляется, а откладывается в браузере;
- в меню ⚙ появился пункт **«Добавить карточки из JSON»** — добавляет карточки
  из файла, ничего не заменяя (старый «Импортировать JSON» заменяет всё).

**Важно про данные, оставшиеся на старом адресе (Vercel).** Хранилище
браузера привязано к адресу сайта. Карточки, внесённые в автономном режиме,
пока портал открывал приложение с Vercel, видны только на старом адресе. Чтобы
их забрать:
1. Не удаляйте проект на Vercel, пока не соберёте данные.
2. Задеплойте туда эту версию кода (из этой ветки).
3. В Битрикс24 создайте **временное** второе локальное приложение с путём
   обработчика на старый адрес Vercel (основное приложение не трогайте).
4. Попросите сотрудников из отделов без данных открыть это временное
   приложение. Оно покажет их карточки; нажмите ⚙ → «Экспортировать JSON» и
   сохраните файл.
5. Затем в основном инфоцентре, в инфоцентре своего отдела: ⚙ → «Добавить
   карточки из JSON».
6. Когда все данные собраны, удалите временное приложение.

**Как найти отделы без данных:** `https://<домен>/api/bitrix-status`, поле
`departmentsWithoutData` — отделы, которые ни разу ничего не сохранили на
сервер; `storedBoards` — какие инфоцентры на сервере есть, сколько в них
карточек и кто правил последним. Если в ответе есть `departmentsError`, значит
серверу не видна сама структура отделов: проверьте `BITRIX_CLIENT_ID`/`SECRET`
и попросите администратора портала один раз открыть приложение.

## Обновление кода

Обычное обновление — **только код и перезапуск службы**:

```bash
BRANCH=<ветка> bash /opt/infocenter-rck/deploy/update.sh
```

`update.sh` не трогает nginx, сертификат, Redis, systemd-юнит и
`/etc/infocenter-rck.env`. Если в `/opt/infocenter-rck` есть правки файлов,
сделанные прямо на сервере, он остановится и покажет их (`FORCE=1` —
обновить, потеряв их).

`install.sh` повторно запускать незачем. Если всё же нужно (например,
переустановить Redis или Node.js):

```bash
DOMAIN=infocenter.2.27.10.126.nip.io BRANCH=<ветка> bash /opt/infocenter-rck/deploy/install.sh
```

Конфиг nginx он не трогает, если уже есть любой конфиг с `server_name` этого
домена, а certbot тогда не запускает. Но systemd-юнит он перезаписывает из
репозитория, а Redis перезапускает.

## Дубль «Инфоцентра РЦК» (dept-115)

Из приложения дубль убран кодом. В Redis он остаётся, пока его не
перенести в архив:

```bash
cd /opt/infocenter-rck && set -a && . /etc/infocenter-rck.env && set +a
node deploy/archive-rck-duplicate.js            # только отчёт
node deploy/archive-rck-duplicate.js --apply    # отчёт + перенос в архив
```

Отчёт делит карточки дубля на «совпадает с РЦК», «в РЦК правили позже» и
**«только в дубле»** — последние в «Инфоцентре РЦК» отсутствуют, и их нужно
просмотреть глазами: сами они никуда не сливаются. `--apply` переименовывает
ключи дубля (данные, снимки, история карточек) в
`rck:archive:dept-115:<дата>:*` — ничего не удаляется, команда возврата
печатается в конце.

## Резервные копии

Сохранять нужно только Redis (`/var/lib/redis`) и
`/var/lib/infocenter-rck/uploads`. Например, так (можно раз в сутки через cron):

```bash
redis-cli BGSAVE && sleep 5 && tar czf /root/infocenter-$(date +%F).tgz /var/lib/redis /var/lib/infocenter-rck/uploads
```
