# Инфоцентр РЦК — как это устроено

Дашборд для ЦПП Калининградской области (React + Vite + TypeScript + Recharts),
встроен в Битрикс24 как локальное приложение.

**28.08.2026 — починено сохранение карточек, добавлена история версий.**

1. **Симптом.** Сотрудники вносили изменения, они появлялись на полсекунды и
   пропадали. Причина — состояние дашборда целиком писалось в одну опцию
   приложения Битрикс24 (`app.option.set`, ключ `rck_dashboard_v1`). Значение
   опции ограничено по объёму, и после появления карточек-изображений
   (`data:`-URL в base64) и таблиц запись стала отказывать. Клиент при этом
   перечитывал `app.option` при каждом возврате фокуса на вкладку и
   безусловно затирал локальное состояние старым ответом портала — правка
   исчезала прямо на глазах. Второй множитель: чтение затирало данные даже
   тогда, когда сохранение ещё выполнялось (гонка «сохраняю ↔ читаю»).

2. **Что сделано.**
   - Состояние дашборда переехало в Redis (`api/_store.js`, ключ
     `rck:dashboard:current`) — тот же инстанс, где лежит сервисный токен.
     Ограничение на объём опции портала больше не действует; предел — 3,5 МБ
     на весь инфоцентр, при превышении сотрудник видит понятную ошибку.
   - Ранее внесённые данные переносятся из `app.option` автоматически при
     первом чтении, пока в Redis пусто. Резервная копия продолжает писаться в
     `app.option`, пока дашборд помещается в опцию (до ~48 КБ), но её отказ
     больше не ломает сохранение.
   - Чтение и запись идут через новый эндпоинт `/api/dashboard`
     (`load`/`save`/`history`). Старый `/api/save-dashboard` остался для вкладок
     со старым бандлом и пишет в то же хранилище.
   - Клиент (`src/store.ts`) больше не затирает несохранённые правки: чтение с
     сервера пропускается, пока есть локальные изменения или идёт сохранение;
     сохранение ставится в очередь (debounce 500 мс), повторяется с
     нарастающей паузой при ошибке и переживает протухший токен вкладки
     (`BX24.refreshAuth`).
   - Правки двух вкладок сливаются по карточкам (трёхстороннее слияние по
     снимку версии, от которой отталкивалась вкладка) вместо last-write-wins.
   - Если в браузере остались правки, не доехавшие до портала из-за старой
     ошибки, при открытии показывается баннер: отправить их на портал или
     открыть версию портала. Молча они не пропадают.
   - У каждой карточки появилась «История изменений» — ползунок по сохранённым
     версиям (дата, автор, восстановление). Хранится в Redis:
     `rck:card-history:<вкладка>:<id карточки>`, до 40 версий и ~700 КБ на
     карточку; изображения в тяжёлых версиях не дублируются.
   - Загружаемые картинки ужимаются в браузере (до 1600 px, JPEG) — чтобы
     инфоцентр снова не распух до неподъёмного размера.

**28.08.2026 — инфоцентр каждого отдела в одном приложении.**

1. Приложение одно, инфоцентров много: по одному на каждый отдел из структуры
   Битрикс24. Сотруднику сразу открывается инфоцентр его отдела; какие
   инфоцентры ему доступны, решает сервер (`api/_access.js`) — идентификатор
   инфоцентра из запроса всегда сверяется с этим списком, подменить его нельзя.

2. Правила доступа:
   - **сотрудник** — свои отделы (`UF_DEPARTMENT`) смотрит и правит,
     вышестоящие подразделения только смотрит;
   - **руководитель** (`UF_HEAD` отдела) — свой отдел и все его подотделы,
     с правом правки;
   - **директор** — руководитель корневого отдела, поэтому по тому же правилу
     получает всю структуру; дополнительно можно перечислить ID в
     `INFOCENTER_DIRECTOR_IDS`;
   - **администратор портала** — все инфоцентры;
   - **сводный экран** (выбранная вкладка по всем доступным отделам, только
     просмотр) — у всех, кому доступно больше одного инфоцентра.

3. Хранилище: у каждого инфоцентра свои ключи Redis
   (`rck:board:<id>:current`, `rck:card-history:<id>:<вкладка>:<карточка>`).
   Исторические данные РЦК никуда не переносились — они остались под префиксом
   `rck` и доступны как общий инфоцентр «РЦК (общий)», пока не указан
   `INFOCENTER_LEGACY_DEPARTMENT_ID`.

4. Если структура отделов недоступна (не выданы права, сбой портала),
   приложение не запирает никого: все получают общий инфоцентр РЦК ровно так,
   как он работал до разделения, плюс предупреждение в шапке.

**07.09.2026 — копия инфоцентра РЦК у отдела «Региональный центр компетенций в
сфере производительности труда».**

1. `api/_seedCopy.js` — разовая копия: содержимое исторического инфоцентра РЦК
   (префикс `rck`) записывается в инфоцентр отдела. Исходный инфоцентр РЦК не
   меняется ничем: это копия, а не переезд, и он по-прежнему виден как
   отдельный борд «РЦК».

2. Когда: при первом же открытии приложения (действие `bootstrap`). Отдел
   ищется по названию, устойчиво к регистру, «ё» и лишним пробелам; можно
   задать явно переменными `INFOCENTER_RCK_COPY_DEPARTMENT_ID` или
   `INFOCENTER_RCK_COPY_DEPARTMENT_NAME`.

3. Копия одноразовая и не мешает работе отдела:
   - отметка `rck:legacy-copy:<инфоцентр>` в Redis ставится через `SET NX`
     (два одновременных открытия не запустят копирование дважды) и навсегда
     закрывает повтор — правки отдела ничем не перетираются;
   - инфоцентр, в котором уже есть карточки, не трогается вообще (в отметке
     остаётся «пропущено»); перезаписать его можно только осознанно —
     `INFOCENTER_RCK_COPY_OVERWRITE=1` плюс удаление отметки;
   - если инфоцентр РЦК в этот момент пуст, отметка снимается и попытка
     повторится при следующем открытии;
   - ошибка копирования не роняет открытие приложения — она только пишется в
     лог функции.

4. Результат виден на `/api/bitrix-status` в поле `legacyCopy`: статус, отдел,
   число карточек и время.

**07.09.2026 — история только в редактировании, картинки во весь экран, ширина
столбцов таблиц.**

1. «История изменений» больше не видна в режиме просмотра: таймлайн рисуется
   только в режиме редактирования (`src/components/TabBoard.tsx`). При выходе
   из режима выбранная прошлая версия сбрасывается — иначе карточка осталась бы
   показывать её без возможности вернуться, ведь таймлайн уже скрыт.

2. Изображение в карточке открывается во весь экран — кнопкой в углу картинки
   или щелчком по ней (`src/components/cards/ImageLightbox.tsx`). Закрывается
   фоном, крестиком и Esc. Рисуется порталом в `body`: карточки лежат внутри
   анимированных контейнеров с `transform`, а внутри такого контейнера
   `position: fixed` отсчитывается от него, а не от окна.

3. Таблицы: текст в ячейках переносится по словам (`whitespace-pre-wrap
   break-words`), а ширину столбцов можно задать — поле в пикселях под
   заголовком столбца в редакторе или перетаскивание правой границы заголовка
   (двойной щелчок — «авто»). Ширины лежат в карточке как `columnWidths`
   (`src/types.ts`), выровнены по столбцам и переезжают вместе с ними при

   `table-fixed` с `minWidth` по сумме ширин, иначе браузер считает ширину
   подсказкой и растягивает столбец под содержимое.

## Хостинг: Vercel (GitHub + Vercel, как в infocenter-IIC)

- Репозиторий подключён к проекту Vercel; автодеплой при пуше в `main`.
- `vercel.json` — маршрутизация: `/api/dashboard`, `/api/save-dashboard` и
  `/api/bitrix-status` на свои serverless-функции, всё остальное — на
  `api/serve.js`.
- `api/serve.js` — раздаёт `dist/` для ЛЮБОГО HTTP-метода. Обычная
  статическая раздача Vercel отвечает на POST ошибкой `405`, а Битрикс24
  открывает локальное приложение именно POST-запросом (передаёт токен
  авторизации во внутренний iframe) — поэтому весь трафик идёт через
  serverless-функцию. На POST дополнительно вызывает `maybeCaptureServiceToken`
  из `_bitrixAuth.js` (см. ниже).
- Деплой при необходимости вручную: `npm run build`, затем пуш в `main` —
  Vercel собирает и раздаёт `dist/` сам (buildCommand/outputDirectory заданы
  в `vercel.json`).

## Как дашборд получает и сохраняет данные

Данные карточек лежат в Redis, доступ к ним — через свои serverless-функции:

1. Сотрудник открывает пункт меню → Битрикс24 грузит `index.html` в `iframe`
   и передаёт туда токен авторизации POST-запросом. `api/serve.js`
   перехватывает этот POST: если в теле есть `AUTH_ID`/`REFRESH_ID`
   администратора портала, `maybeCaptureServiceToken` (`api/_bitrixAuth.js`)
   меняет их на сервисный токен и сохраняет его в Redis — это нужно один раз,
   дальше он обновляется через `refresh_token`.
2. `index.html` условно подключает SDK Битрикс24
   (`api.bitrix24.com/api/v1/`) — **только если страница открыта внутри
   iframe** (`window.self !== window.top`), иначе при прямом заходе дашборд
   показывает «Автономный режим» на `localStorage`.
3. **Чтение**: `POST /api/dashboard` с `action: "load"` и токеном сотрудника
   (`BX24.getAuth()`). Функция проверяет сессию через `profile` и отдаёт
   состояние из Redis. Если в Redis пусто — один раз переносит туда то, что
   было сохранено в `app.option`. Если наш сервер недоступен, браузер
   запасным путём читает `app.option` напрямую (`app.option.get` доступен
   любому сотруднику).
4. **Запись**: `POST /api/dashboard` с `action: "save"`, состоянием и номером
   версии, от которой отталкивалась вкладка (`baseRev`). Функция проверяет
   сессию, при необходимости сливает правки с чужими и пишет в Redis.
   Запись `app.option` осталась резервной копией — на сохранение её отказ не
   влияет.
5. **История карточки**: `POST /api/dashboard` с `action: "history"`,
   `tab`, `cardId` — версии от старых к новым для ползунка на карточке.
6. **Сводный экран**: `POST /api/dashboard` с `action: "summary"` и вкладкой —
   карточки этой вкладки по всем доступным инфоцентрам. Настройка сводки
   (какие отделы, в каком порядке и какие карточки на неё тянуть) читается и
   пишется действиями `action: "summary-config"` и
   `action: "summary-config-save"`; она личная и хранится под сотрудником.

   Ключи в Redis: `rck:dashboard:current` (актуальное состояние),
   `rck:dashboard:snap:<rev>` (снимки для слияния, сутки),
   `rck:card-history:<вкладка>:<id>` (история карточек),
   `rck:summary-config:<id сотрудника>` (личная настройка сводного экрана),
   `rck:bx-service-token` (сервисный токен). Все с префиксом `rck` — не
   пересекаются с ключами infocenter-IIC, даже если базы общие. Ключ опции
   портала для резервной копии и переноса — `rck_dashboard_v1`.

Диагностика (не раскрывает сам токен):
**https://\<домен-проекта-на-vercel\>/api/bitrix-status**

## Обязательная настройка на Vercel (один раз, для записи карточек)

Redis обязателен — в нём живут данные инфоцентра. Без него дашборд открывается,
но сохранение падает с понятной ошибкой в шапке, а карточки остаются только в
`localStorage` того, кто их правил (и предлагаются к отправке при следующем
открытии). Сервисный токен администратора на сохранение больше не влияет — он
нужен только для переноса старых данных из `app.option` и резервной копии туда.

1. **Redis**, вариант на выбор:
   - **Переиспользовать базу infocenter-IIC** (рекомендуется — не нужен
     второй бесплатный инстанс, данных там крохи: один токен + JSON
     дашборда). В проекте infocenter-IIC на Vercel → **Storage** → у
     существующей Redis-базы → **Connect to Project** → выбрать проект
     infocenter-RCK. Vercel сам пропишет `REDIS_URL` в РЦК — руками строку
     подключения копировать не нужно. Безопасно: ключи в Redis у РЦК и ИИЦ
     с разными префиксами (`rck:bx-service-token`/`rck_dashboard_v1` против
     `iic:bx-service-token`/`iic_dashboard_v1`, см. `api/_bitrixAuth.js` и
     `api/save-dashboard.js`) — не пересекутся, даже деля одну базу.
   - Либо отдельная база: **Storage → Create Database → Redis** (Redis
     Cloud) → подключить к проекту. Storage Type — **RAM only**, план
     **Free (30 MB)**. При создании в поле **Custom Prefix** указать
     `REDIS` — тогда Vercel сам создаст переменную `REDIS_URL`.
2. В **Settings → Environment Variables** проекта РЦК добавить:
   - `BITRIX_CLIENT_ID` — «Ключ приложения» локального приложения РЦК в Б24
   - `BITRIX_CLIENT_SECRET` — «Секретный ключ» оттуда же

   Необязательные переменные для инфоцентров по отделам (меняются в том же
   разделе, без правок кода):
   - `INFOCENTER_LEGACY_DEPARTMENT_ID` — ID отдела, которому принадлежат
     исторические данные РЦК. Пока не задан, они видны всем как отдельный
     инфоцентр «РЦК (общий)». Когда задан — открываются в инфоцентре этого
     отдела, без переноса данных и с сохранением нумерации версий.
   - `INFOCENTER_HIDDEN_DEPARTMENTS` — ID отделов через запятую, для которых
     инфоцентр не нужен (например, технические подразделения).
   - `INFOCENTER_RCK_COPY_DEPARTMENT_ID` / `INFOCENTER_RCK_COPY_DEPARTMENT_NAME` —
     куда один раз скопировать инфоцентр РЦК (по умолчанию ищется отдел
     «Региональный центр компетенций в сфере производительности труда»);
     `INFOCENTER_RCK_COPY_OVERWRITE=1` разрешает перезаписать непустой
     инфоцентр отдела — по умолчанию такой инфоцентр не трогается.
   - `INFOCENTER_DIRECTOR_IDS` — ID сотрудников, которым нужен доступ ко всем
     инфоцентрам, если они не значатся руководителями в структуре.

   Именно с такими именами, без суффиксов (`_01` и т.п.) не нужны —
   Environment Variables заданы на уровне проекта Vercel, у РЦК и ИИЦ они
   в разных проектах и никак не пересекаются, даже если оба указывают на
   одну Redis-базу из пункта 1.
3. Передеплоить проект (если переменные добавлялись после последнего
   деплоя).
4. Попросить администратора портала **один раз открыть приложение** в
   Битрикс24 (полная перезагрузка страницы, не просто переключение вкладки
   браузера) — это момент, когда сервер получает и сохраняет сервисный токен.
   Он нужен для переноса ранее внесённых карточек из `app.option` и для
   резервной копии; сохранять карточки сотрудники смогут и без него.

Если сервисный токен по какой-то причине перестанет обновляться (например,
приложение долго не переоткрывали) — попросить администратора снова открыть
приложение один раз; текущее состояние видно на `/api/bitrix-status`.

## Настройка в Битрикс24

Приложения → Разработчикам → Другое → Локальное приложение:
- Путь обработчика: URL проекта на Vercel
- Права: нужны **«Пользователи» (`user`)** и **«Структура компании»
  (`department`)** — по ним определяются отдел открывшего сотрудника и
  руководители подразделений. Без них инфоцентры по отделам не включатся:
  все увидят общий инфоцентр РЦК и предупреждение в шапке. Scope `lists`
  больше не нужен (Списки не читаются). Проверить, видит ли приложение
  структуру, можно на `/api/bitrix-status` — поля `departments` и
  `departmentsError`.
- «Использует только API» и BitrixMobile — выключены
- Закрепить пункт меню звёздочкой «В избранное» — новые приложения уходят в
  конец списка «Ещё»
- Скопировать **«Ключ приложения»** (client_id) и **«Секретный ключ»**
  (client_secret) со страницы этого локального приложения — для переменных
  окружения на Vercel, см. выше
